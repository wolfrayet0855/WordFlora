# Endgame and weather events: technical, platform and policy constraints (research, 2026-11-04)

Scope: (1) an endgame after all 50 plants / all 5 levels; (2) deterministic "weather event" days (drought, termites, big storm, frost, heat wave, hail, flood) that set plants back visually, or in an opt-in "Wild Weather" mode, with a day-before warning, Shed shelter tools and a hard optional rescue puzzle. Builds on `docs/research/apple-capabilities.md` (cited below as **[AC §n]**); it does not repeat that doc's notification, widget and SwiftData basics, it extends them.

Evidence tiers (same as [AC §0]):
- **[A]** Apple primary text fetched on 2026-11-04 (developer.apple.com page JSON, App Review Guidelines, App Store Connect help).
- **[P]** Other primary text fetched on 2026-11-04 (Federal Register, W3C, ICO code text via mirror).
- **[B]** Secondary source (law firm or press), searched on 2026-11-04.
- **[T]** Training knowledge, not re-fetched. **UNVERIFIED** means I tried and could not confirm.

Repo facts this research relies on (read on 2026-11-04):
- `PlantCollectible.stage` is documented "forward-only" and `DataReconciler.merge` takes `max` of `stage`, `growthPoints`, `earnedCount`, `currentLevel`, `plantsEarnedThisLevel` and nearly every counter (`WordFlora/Storage/DataReconciler.swift` lines 31-41, 65-67).
- `GardenBackup.merge` reuses those rules and promises "a restore never lowers progress" (`WordFlora/Storage/GardenBackup.swift` lines 6-7, 142, 154).
- `WakePuzzle` seeds `SplitMix64` with `FNV-1a(plantId) ^ day * 0x9E3779B97F4A7C15`, and `day(for:)` counts days from 2026-01-01 built with `Calendar.current` (`WordFlora/Rules/WakePuzzle.swift` lines 38-41, 44-48, 67).
- Reminders are already `.passive`, at most one a day, shared between kinds, never 21:00-08:00, stop after 3 days without a visit, max 3 scheduled, and `removeAllPendingNotificationRequests()` on every replan (`WordFlora/Notifications/Reminders.swift` lines 4-10, 90, 111, 116).
- Game audio uses `.ambient` (`WordFlora/Audio/Sound.swift:112`); read-aloud uses `.playback` + `.spokenAudio` (`WordFlora/Audio/ReadAloud.swift:63`), so it ignores the silent switch.
- Deployment target is iOS 17.5 in the project file (the brief says iOS 18; anything iOS 18-only below gets an `#available` note).
- Owner ruling: "nothing earned is ever removed"; Quiet Garden and Calm mode turn loss visuals off (`docs/STATUS.md`, rulings of 2026-11-03).

## 0. Constraints that bind the design

| # | Level | Constraint | Why (source) |
|---|---|---|---|
| 1 | **MUST** | A weather setback never writes a lower value into `stage`, `growthPoints`, `earnedCount`, level or any counter that is merged by `max`. Model setbacks as a **derived overlay**: `shownStage = stage - activeSetback(plant, today)`, where `activeSetback` is computed and not stored. | A stored drop is undone on the next iCloud reconcile or backup restore (`DataReconciler.swift:65-67`, `GardenBackup.swift:6-7`), and it breaks the owner rule "nothing earned is ever removed". |
| 2 | **MUST** | Same rule for the endgame: any "prestige", "new season" or "replant" loop is a **new monotonic counter** (`cycle`, `seasonsCompleted`), never a reset of existing counters. | Same `max` merges; a reset on device A comes back from device B. |
| 3 | **MUST** | Event for a day = pure function `f(weatherSeed, dayKey, algoVersion)`. No stored "event happened" rows. | No server; CloudKit order is indeterminate [A, §5]; pure functions make every device agree once the seed is shared. |
| 4 | **MUST** | `dayKey` from `Calendar(identifier: .gregorian)` with `TimeZone.current`, as `yyyy-MM-dd` or a Gregorian day number. Do **not** reuse `WakePuzzle.day` as is. | `WakePuzzle.day` builds its 2026-01-01 epoch with `Calendar.current`; on a device set to the Buddhist or Japanese calendar that is a different instant, so two devices with different calendar settings disagree (`WakePuzzle.swift:38-41`). |
| 5 | **MUST** | Rescues are stored as **insert-only rows** (or a set field merged by union in `DataReconciler`), keyed by `(plantId, eventDayKey)`. Merges are idempotent. | CloudKit has no unique constraints [A]; a JSON set field resolved last-writer-wins drops a concurrent append [T]. |
| 6 | **MUST** | New fields are optional or defaulted; new relationships optional with an inverse; no `@Attribute(.unique)` / `#Unique`; no Deny delete rule. Deploy the CloudKit schema to Production before release; after that, changes are additive only. | Apple, "Creating a Core Data Model for CloudKit" and "Syncing model data" [A, §5]. |
| 7 | **MUST** | The day-before warning is a local notification at `.passive` (at most `.active`), sent through the existing one-a-day reminder slot and opt-in. **Never `.timeSensitive`, never `.critical`.** | HIG: Time Sensitive is for "an event that's happening now or will happen within an hour" [A, §1]. A storm "tomorrow" fails that test on its face. |
| 8 | **MUST** | Shelter, protection, recovery and rescue are **never sold** (not as an IAP, not as a Plus perk, not for a rewarded ad), and never have a paid random outcome. | Guideline 5.6 ("prey on users… any other manipulative practices"), 3.1.1 loot-box odds, EU CPC finding that time-limited pressure on children is unfair [A, B, §3-4]. |
| 9 | **MUST** | Flashes (lightning, hail glints) stay at or under 3 per second and small in area; none when Reduce Motion or Dim Flashing Lights is on; every motion has a cross-fade or static variant. | WCAG 2.3.1 [P]; HIG Accessibility [A]; `MADimFlashingLightsEnabled()` [A, §8]. |
| 10 | **MUST** | Do not rely on background execution. Compute weather on launch, on foreground (`scenePhase == .active`) and on `significantTimeChangeNotification`; the widget computes its own line from the shared store. | `BGTaskRequest.earliestBeginDate`: "the system doesn't guarantee launching the task at the specified date" [A, §7]. |
| 11 | **SHOULD** | An event applies only on a day the player opens the app ("presence-based"). Skipped days apply nothing; a return after a gap shows at most one setback. | Kills the clock-skip exploit, and avoids punishing absence (ICO standard 5 engagement concerns [P/B], FTC Section 5 note [P]). |
| 12 | **SHOULD** | Keep a synced `weatherHighWaterDay` (merge `max`). Never apply or re-roll an event for a dayKey below it. | Clock-tamper guard with no server (§6). |
| 13 | **SHOULD** | Wild Weather (a real setback, even as an overlay) is off and hidden for under-13 and unknown age, and behind the parental gate if a parent turns it on; visual-only weather follows the same exemptions as petals (Calm, Quiet Garden). | Kids Category spirit (1.3), ICO nudge and detrimental-use standards, CPC "do not exploit children's vulnerabilities" [A, P, B]. |
| 14 | **SHOULD** | Keep weather art gentle and rare enough to stay out of "Frequent horror or fear themes" (13+). Re-check the age rating questionnaire before shipping. | App Store Connect age rating values: infrequent horror/fear = 9+, frequent = 13+ [A, §3]. |
| 15 | **SHOULD** | Freeze the event generator behind `algoVersion` + a cutover dayKey; a new weather type ships as a new version that applies only from its cutover day. | Otherwise an app update rewrites past and future forecasts on some devices before others update. |
| 16 | **AVOID** | Live Activities, countdown timers (`Text(_:style: .timer)`), "tomorrow only" urgency, red badges, or any copy that frames the event as a deadline. | HIG Live Activities (defined start and end, 8 h) [A, §2]; app's no-urgency copy rule; CPC Star Stable finding [B]. |
| 17 | **AVOID** | Seeding from `identifierForVendor`, the CloudKit user record ID, or any device/user identifier. Use a random 64-bit value generated in-app. | Required-reason/fingerprinting rules and COPPA "persistent identifier" exposure if it ever leaves the device [A, P, §4]. |
| 18 | **AVOID** | Playing weather audio through the read-aloud `.playback` session. | `.playback` ignores the silent switch; `.ambient` respects it [A, §8]. |

## 1. Local notifications for "weather tomorrow"

**Interruption levels, Apple's own definitions [A]** (HIG "Managing notifications", https://developer.apple.com/design/human-interface-guidelines/managing-notifications):
- Passive: "Information people can view at their leisure, like a restaurant recommendation."
- Active (default): "Information people might appreciate knowing about when it arrives, like a score update on their favorite sports team."
- Time Sensitive: "Information that directly impacts the person and requires their immediate attention, like an account security issue or a package delivery."
- Critical: "Urgent information about health and safety… extremely rare", and needs an entitlement.
- Best practice, verbatim: "Use the Time Sensitive interruption level only for notifications that are relevant in the moment… make sure the notification is about an event that's happening now or will happen within an hour." And: "You don't want people to feel that a notification uses a high level of urgency to interrupt them with low-priority information." The system also prompts people the first time and periodically to turn Time Sensitive off.
- `UNNotificationInterruptionLevel.timeSensitive`: "breaks through system notification controls… such as Notification Summary and Focus" [A] https://developer.apple.com/documentation/usernotifications/unnotificationinterruptionlevel/timesensitive . It also needs the Time Sensitive Notifications capability added to the target (forum thread, https://developer.apple.com/forums/thread/683630 [B]); I could not fetch the entitlement reference page (UNVERIFIED wording).

**Ruling: `.passive`.** A game warning about tomorrow is a "view at leisure" item. `.active` is defensible only if the player picks a delivery time in Settings (it already does), but `.passive` matches the existing `SystemNotificationCenter` (`Reminders.swift:111`) and the calm brand. `.timeSensitive` fails the HIG's "within an hour" test and would also bypass a child's School or Sleep Focus, which is the opposite of what a parent expects. Never `.critical`: real weather apps and governments use that channel, and a fake "storm" alert from a game could alarm a child (and an adult) in a region with real storms.

**Focus and summaries [A]:** Focus "might delay the delivery of a notification alert", and people choose which apps break through. Passive items fall into Scheduled Summary. Apple Intelligence summaries can rewrite copy [AC §5]: a title like "Big storm tomorrow" next to a real weather app could summarize into something alarming. Put "garden" in the title and keep the body to one idea.

**64 pending cap:** the system keeps the soonest-firing 64 requests per app (Apple doc wording quoted second-hand; Apple engineer on https://developer.apple.com/forums/thread/811171 [B]). Not a real constraint here: schedule at most the next one or two weather warnings inside the existing `ReminderPolicy.maxScheduled = 3`. **Integration trap:** `ReminderScheduler.plan` calls `removeAllPending()` (`Reminders.swift:90,116`), so a separately scheduled weather request would be wiped on every replan. The warning must be a third `ReminderCopy.Kind` chosen by the same planner (one notification per day total, weather replaces the tending/Daily Bloom line on a warning day), not a second scheduler.

**Permission and provisional:** Apple recommends asking "in context" and offers `.provisional`, which delivers quietly to Notification Center history with Keep / Turn Off buttons [A] https://developer.apple.com/documentation/usernotifications/asking-permission-to-use-notifications . Keep the current explicit opt-in [AC §5]; do not add a new prompt for weather. If reminders are off, the warning shows in-app only (Home line, widget line, Shed banner).

**Marketing and kids rules:**
- Guideline 4.5.4 [A]: notifications "must not be required for the app to function" and must not be used "for promotions or direct marketing purposes unless customers have explicitly opted in". HIG: "Never use the Time Sensitive interruption level to send a marketing notification." So the warning may never mention Plus, sales or shelter for sale.
- Guideline 1.3 [A] (spirit; we are not in Kids Category): no "distractions to kids unless reserved for a designated area behind a parental gate".
- FTC [P]: the 2025 COPPA amendments did **not** adopt the proposed limit on using persistent identifiers "in connection with processes that encourage or prompt use", calling it "overly broad", but the Commission "may pursue enforcement under section 5 of the FTC Act in appropriate cases" against prolonged-use practices (90 FR 16918, https://www.federalregister.gov/documents/2025/04/22/2025-05904/childrens-online-privacy-protection-rule). A loss-threat notification to a child is the textbook case for that warning.

**Recommended rules:** opt-in only; default off under 13 and in Calm / Quiet Garden; inherits quiet hours (21:00-08:00) and the 3-days-without-a-visit stop; no sound (passive); `threadIdentifier` "weather"; no badge; no countdown or clock time of the event; never sent for a day on which the player has turned Wild Weather off.

**Copy constraints:** title names the garden; one idea; no deadline; always offer the calm option ("or just enjoy the rain"); no fear words; none of the banned list (miss, lonely, alone, waiting, abandon, neglect, forgot/forget, die/dying/dead, lost, empty, left, broken, hurry, expires, only, last, smart, genius, beat, better than). Examples:
- "Windy day ahead in your garden" / "Tomorrow looks breezy. The Shed has a cozy spot for your plants."
- "Frosty morning tomorrow" / "Your garden may get a sparkly frost. A warm cover from the Shed helps."
- "Rain is on the way" / "Tomorrow brings lots of rain. Your plants can rest in the Shed, or splash about."

## 2. WidgetKit line and Live Activities

**Widget "weather tomorrow" line [A]** (https://developer.apple.com/documentation/widgetkit/keeping-a-widget-up-to-date , https://developer.apple.com/documentation/widgetkit/timelineprovider):
- A frequently viewed widget typically gets "40 to 70 refreshes" per day, entries should be "at least about 5 minutes apart", and "if your widget can predict points in time that it should reload, the best approach is to generate a timeline for as many future dates as possible."
- Weather is fully predictable from the seed, so the provider can return entries at the next two local midnights with `.after(nextMidnight)`: 1-2 reloads a day, no app launch needed. Call `WidgetCenter.reloadAllTimelines()` when the seed is first adopted or merged (§5) and when Wild Weather or Calm toggles.
- The widget already opens the store read-only (`createIfMissing: false`, STATUS 2026-11-03). It needs only `weatherSeed`, `weatherHighWaterDay`, the opt-in flags and the age band; never let it write rescues (two-writer issue is deferred in STATUS).
- Do **not** use `Text(date, style: .timer/.relative)` for the event; show a plain line ("Tomorrow: breezy"), which also suits tinted and accessory families [AC §4].

**Live Activities: no [A].** HIG (https://developer.apple.com/design/human-interface-guidelines/live-activities): "Offer Live Activities for tasks and events that have a defined beginning and end… short to medium duration activities that don't exceed eight hours", and "Don't use a Live Activity to display ads or promotions." ActivityKit (https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities): "A Live Activity can be active for up to eight hours… After the eight-hour limit, the system automatically ends the Live Activity… a Live Activity remains on the Lock Screen for a maximum of 12 hours." A storm warned a day ahead lasts longer than 8 h, is not a real-time event the person is following, and a lock-screen countdown is exactly the urgency the copy rule forbids. [AC §4, §11] already listed Live Activities as "skip"; this feature reinforces that.

## 3. App Store Review Guidelines, age rating and Apple kids guidance

Guidelines text fetched [A] https://developer.apple.com/app-store/review/guidelines/ :
- **1.3 Kids Category:** "must not include links out of the app, purchasing opportunities, or other distractions to kids unless reserved for a designated area behind a parental gate." We are not in the category, but the parental gate already exists; the Wild Weather opt-in for under-13 should sit behind it.
- **3.1.1:** "Apps offering 'loot boxes' or other mechanisms that provide randomized virtual items for purchase must disclose the odds of receiving each type of item to customers prior to purchase." Any paid "mystery shelter" or "random rescue bundle" is a loot box: odds disclosure plus a 9+ rating (below).
- **3.1.2(a):** subscriptions "must provide ongoing value"; "Apps that attempt to scam users… trick users into purchasing a subscription under false pretenses" are removed. 3.1.2(c): "clearly describe what the user will get for the price." Plus remains fine for cosmetics (pots, themes); selling "Plus keeps your plants safe from storms" describes value that exists only because the game created the threat.
- **5.6 Developer Code of Conduct:** "Apps should never prey on users or attempt to rip off customers, trick them into making unwanted purchases… or engage in any other manipulative practices within or outside of the app." "Repeated manipulative or misleading behavior… will lead to your removal from the Apple Developer Program."
- **5.1.4 Kids:** apps that collect personal information from a minor "must include a privacy policy and must comply with all applicable children's privacy statutes." Weather adds no data collection if the seed stays in the user's private iCloud (§4).
- **2.5.19** "Don't include any hidden, dormant, or undocumented features": the Wild Weather mode and its setbacks must be explained in-app (and ideally in the App Store description), not appear as a surprise.
- **4.5.4** push notifications: see §1.
- The guidelines contain no literal "dark patterns" section (searched; not present); 5.6 plus 3.1.2(a) is the hook App Review uses.

**Plain answer: would selling shelter or recovery, even via Plus, be risky? Yes, high risk.** It is "pay to stop a loss the game inflicts", aimed at an audience that includes children. In order of severity: (a) a paid random recovery = loot box (3.1.1 odds + 9+ rating); (b) paid shelter/recovery = a 5.6 "manipulative practice" argument and, in the EU, the CPC Network's position on pressuring children (§4); (c) a rewarded ad for recovery for adults is the same mechanic with ads (2.5.18 forbids ads that "manipulate or trick users"), and under-13 already has no ads. Shelter and rescue must be earnable by play and free. Plus can add **cosmetic** weather extras (a rainbow sky after rain, a decorative greenhouse skin) that change no outcome.

**Would loss mechanics for children draw review or regulatory risk?** App Review: low if free, explained, opt-in and reversible; it is not a guideline violation to have plants wilt. Regulatory: moderate if the loss is paired with notifications, absence penalties or any payment, because that is what the FTC Section 5 note, the ICO children's code and the CPC principles target (§4). The overlay design (§0 rows 1, 11, 13) keeps it on the safe side.

**Age rating [A]** (App Store Connect help, https://developer.apple.com/help/app-store-connect/reference/app-information/age-ratings-values-and-definitions/): tiers are 4+, 9+, 13+, 16+, 18+. "Horror/Fear Themes: Content or storylines that evoke feelings of anxiety, dread, or terror" — **infrequent = 9+, frequent = 13+**. "Loot boxes" = 9+. "Parental controls", "Age assurance", "Advertising" and "Infrequent contests" are allowed at 4+. A weekly cartoon breeze with smiling plants is not horror; a dark hurricane with crashing debris and a "your plant may not survive" frame could be judged fear content and, if it is a regular weekly mechanic, "frequent". Apple's new questionnaire deadline was 2026-01-31 ([AC §6], 9to5Mac [B]); answers must be revisited for this feature. Apple's kids page [A] (https://developer.apple.com/app-store/kids-apps/) notes `ageRatingCode` and the Significant Change API "where required by law": **if this feature raises the rating, regulated regions (US state laws, [AC §6]) may require new parental consent**, a second reason to keep the visuals gentle.

**Apple "Designing for kids":** I could not fetch a HIG page by that name (the URL returned Apple's 404 JSON; UNVERIFIED that such a HIG page exists under that title). Apple's current kids guidance is the Kids page above plus 1.3 / 5.1.4. Its parental gate definition: "adult-level tasks… to prevent kids from engaging in certain activities without their parent's knowledge — such as buying Apple In-App Purchases… or following link outs".

## 4. Child-protection law relevant to loss and FOMO mechanics

**COPPA (US), amended rule [P]** — 90 FR 16918, FR Doc. 2025-05904, published 2025-04-22, effective 2025-06-23, compliance by 2026-04-22: https://www.federalregister.gov/documents/2025/04/22/2025-05904/childrens-online-privacy-protection-rule .
- Push-engagement proposal not adopted (quoted in §1), with the explicit Section 5 enforcement caveat.
- Data angle: a random weather seed stored in the player's **private** CloudKit database is not collected by the operator (we cannot read private databases [T]). If it were ever sent to us or an SDK (analytics, ads) it would be a "persistent identifier" under 16 CFR 312.2 [T]. Rule: the seed never leaves SwiftData/CloudKit, is never logged, and is excluded from any analytics or crash payload. It may go into the user-held `GardenBackup` file (user-held, like the nickname).
- FTC enforcement context [B]: Epic Games paid $245 M (2023 order) for design tricks driving unintended purchases, alongside a $275 M COPPA penalty (https://www.ftc.gov/node/80648 copy of the release; original URL UNVERIFIED). The FTC staff report "Bringing Dark Patterns to Light" (2022) exists [T, not re-fetched].

**UK Age Appropriate Design Code (ICO) [P via mirror, B]** — text from https://edlaw.eduverse.com/docs/jurisdiction/nat/gb/childrens-code/STANDARDS.md (the ICO site returned 403 to automated fetches: https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/childrens-information/childrens-code-guidance-and-resources/age-appropriate-design-a-code-of-practice-for-online-services/13-nudge-techniques/):
- Standard 13: "Do not use nudge techniques to lead or encourage children to provide unnecessary personal data or turn off privacy protections." The final standard is data-focused; the 2019 draft also said "or extend their use", which was dropped (search snippet [B]).
- Standard 5: "Do not use children's personal data in ways that have been shown to be detrimental to their wellbeing, or that go against industry codes of practice, other regulatory provisions, or Government advice." ICO guidance under standard 5 names "reward loops", streaks, notifications and auto-play as strategies to extend engagement and warns against personal-data-driven incentives to keep children playing (as reported by PYMNTS / SuperAwesome [B]; ICO page itself UNVERIFIED on 2026-11-04).
- Practical reading: the code bites where **personal data** drives the nudge. Our weather is driven by a random seed and the calendar, not by profiling, and that keeps it out of the core of the code. Do not personalize events by engagement ("players who return less get gentler storms" would use behavior data to steer a child). Keep the settings default "high privacy" and the off-switch obvious.

**EU [B/T]:**
- DSA Article 28(1) (providers of **online platforms** accessible to minors must ensure "a high level of privacy, safety, and security of minors" [T]) applies to online platforms, i.e. hosting services that disseminate user content to the public. WordFlora has no user content distribution, so Art. 28 likely **does not apply directly** [T, not legal advice]. The Commission's 2025-07-14 Art. 28 guidelines still serve as a benchmark: they ask for protection against "commercial practices that may be manipulative, lead to unwanted spending or addictive behaviours, including certain virtual currencies or loot-boxes" (Osborne Clarke / Hunton summaries [B]: https://www.osborneclarke.com/insights/new-european-guidelines-issued-protect-minors-digital-environment). Exact "fear of missing out" wording in the final guidelines: UNVERIFIED.
- CPC Network "Key principles on in-game virtual currencies" (2025-03-21) [B] (https://esportslegal.news/wp-content/uploads/2025/03/Key-principles-on-in-game-virtual-currencies.pdf, Reed Smith Q&A https://www.reedsmith.com/en/perspectives/2025/03/qas-on-the-eu-consumer-protection-authorities-joint-guidance-paper): non-binding, but enforced via the UCPD; the parallel Star Stable action found "pressuring techniques such as time-limited offers to unduly influence children". A paid "save your garden before the storm" is that pattern.
- UCPD Annex I point 28 bans "a direct exhortation to children to buy" [T, not re-fetched]. A shelter-for-sale prompt shown to a child fits.
- Digital Fairness Act: not yet proposed; most recent reports point to a Commission proposal around November 2026, with addictive design and minors among the targets [B] (https://digitalfairnessact.com/commission-pushes-digital-fairness-act-to-mid-2026). UNVERIFIED final scope. Design for it now: no paid loss relief, easy opt-out, no countdowns.

## 5. CloudKit + SwiftData: storing the seed, rescues and endgame state

**Apple rules [A]:**
- "SwiftData framework does include a small number of features that CloudKit doesn't support natively, such as unique constraints and nonoptional relationships"; "CloudKit schemas are additive only, which means you're unable to delete model types or change existing model attributes after you promote a schema to production" (https://developer.apple.com/documentation/swiftdata/syncing-model-data-across-a-persons-devices). Also: "CloudKit processes changes in an indeterminate order."
- Core Data model for CloudKit (https://developer.apple.com/documentation/coredata/creating-a-core-data-model-for-cloudkit): "Unique constraints aren't supported"; "All relationships must be optional"; "All relationships must have an inverse, in case the records synchronize out of order"; "CloudKit doesn't support the Deny deletion rule"; production record types and fields "are immutable and exist for all time." Suggested strategies include "Incrementally add new fields to existing record types" and a `version` attribute.
- Deploying (https://developer.apple.com/documentation/cloudkit/deploying-an-icloud-container-s-schema): "you can't delete record types or fields that are already in production."
- "All attributes optional or defaulted": not stated in the pages I fetched (the attribute row lists unsupported types only); it is the standard NSPersistentCloudKitContainer requirement and the repo already follows it (`PlayerProfile` defaults every field) [T].
- Migration: `VersionedSchema` + `SchemaMigrationPlan` (https://developer.apple.com/documentation/swiftdata/schemamigrationplan [A, title/abstract only]). Adding defaulted properties or a new model is a lightweight migration and needs no custom stage [T]. The repo has no `VersionedSchema` yet; adopt one before the **first Production schema deploy** so later custom stages are possible.
- Conflicts: SwiftData/CloudKit resolves by last writer, so app-level `max`/union merges must run in `DataReconciler` [AC §7], [T].

**Proposed fields (all additive, defaulted):**

| Where | Field | Default | Merge in `DataReconciler` / `GardenBackup` |
|---|---|---|---|
| `PlayerProfile` | `weatherSeed: String` (16 hex chars) | `""` | Non-empty beats empty. Both set and different: keep the seed of the profile with the **earliest `createdAt`**, ties broken by the **lexicographically smaller** seed. Independent of which profile is the keeper (the keeper is chosen by `gamesPlayed`, `DataReconciler.swift:15`), so every device lands on the same seed. |
| `PlayerProfile` | `weatherSeedAdoptedDay: Int` | `0` | Travels with the winning seed. Events before this day are never applied (so a seed swap after first sync cannot retro-damage). |
| `PlayerProfile` | `weatherHighWaterDay: Int` | `0` | `max`. |
| `PlayerProfile` | `wildWeatherOn: Bool` + `wildWeatherChangedAt: Date` | `false`, `.distantPast` | Later `ChangedAt` wins (a toggle is a choice, like `potChosenAt`). |
| `PlayerProfile` | `seasonsCompleted: Int` (endgame cycle) | `0` | `max`. Never reset other counters. |
| new `WeatherRescue` model | `plantId: String`, `eventDay: Int`, `rescuedAt: Date` | `""`, `0`, `.now` | Insert-only. Duplicates allowed; reconciler dedupes by `(plantId, eventDay)`, keeps earliest `rescuedAt`. Union semantics, idempotent. |
| alternative | `rescuedJSON: String` on `PlayerProfile` | `""` | Set union in `DataReconciler`, like `BadgeState.merged`. Smaller schema, but a concurrent append on two devices can be dropped by last-writer-wins until the next reconcile; acceptable only because a rescue can be redone. |
| `GardenBackup.Profile` | the above as optionals | `nil` | Same rules; `isPlausible` checks seed length and non-negative days. |

Seed generation: `UInt64.random(in:)` via `SystemRandomNumberGenerator`, created lazily on first need (not in `init()`, which runs for the throwaway carrier profile in `GardenBackup.merge`, `GardenBackup.swift:134`). Generate only when the store says it has no seed **after** the launch reconcile, to cut the "two devices, two seeds" window.

Why pure functions instead of "event happened" records: (1) two devices that both record "storm on day N for the rose" make duplicates with no unique constraint to stop them; (2) out-of-order delivery can resurrect a cleared event; (3) the widget and the notification planner can compute the forecast without writes; (4) tests are trivial (`f(seed, day)` golden table). Stored state is limited to things the player did (rescues, toggles), all with monotonic or latest-choice merges.

Generator sketch (mirrors `WakePuzzle` so the team knows it): `rng = SplitMix64(seed: seed ^ FNV1a("wx\(algoVersion)-\(dayKey)"))`; roll the chance (e.g. about one event a week, never on two days in a row, a calm day forced after each event); pick the type from a season-weighted table (frost not in July in the north; the hemisphere can come from the locale region, never location services); pick at most one or two affected plant ids by hashing `seed ^ dayKey ^ plantId`. `activeSetback(plant, today)`: the most recent event day `d` affecting the plant with `d >= weatherSeedAdoptedDay`, `d` a day the app was opened (§6), not rescued, and `today - d < healDays` (auto-heal after a few days even without rescue), capped at 1 stage and floored so the plant never shows below stage 1 or below its pot art.

## 6. Time, calendar and clock tampering

- **Day definition:** local calendar day in `TimeZone.current`, Gregorian (§0 row 4). Compute with `calendar.startOfDay` + `dateComponents([.day], from:to:)`, as `WakePuzzle` does, which handles DST days of 23 or 25 hours correctly; never `86_400`-second arithmetic. Recompute on `UIApplication.significantTimeChangeNotification` ("a change to a new day (midnight), a carrier time update, or a change to, or from, daylight savings time" [A]) and `NSSystemTimeZoneDidChange` [A].
- **Two time zones:** a traveller's two devices can disagree for a few hours about "today". Harmless: rescues are keyed by the event's dayKey, the high-water mark is a `max`, and the overlay is recomputed per device.
- **Clock tampering threats:** (a) set the clock back to escape a storm: the high-water guard ignores days below `weatherHighWaterDay`, so the storm is still the "current" event; (b) set it forward to skip a warned storm or to farm events: presence-based application means skipped days do nothing, and forward-jump-then-return pins the high-water mark in the future, which only gives fewer events until the real date catches up (benign); (c) jump to farm rescue rewards: rescue gives back the overlay only; if it gives a reward (Shed points, a badge), cap it per real day using the high-water day and a lifetime count.
- `NSSystemClockDidChange` [A] fires when the clock is changed by the user; use it only to re-run the computation, not to accuse or punish.
- **Uptime-based checks** (`ProcessInfo.systemUptime`) are a Required Reason API with fingerprinting warnings [A] (https://developer.apple.com/documentation/foundation/processinfo/systemuptime); not worth it for a cozy game. A server-free check cannot be tamper-proof; the design goal is "cheating gains nothing", not "cheating is detected".
- **Catch-up cap:** after any gap, at most one active setback per plant and at most two plants affected garden-wide; nothing stacks.

## 7. Background execution

- `BGAppRefreshTask`: "a short task typically used to refresh content"; the system "provides your app up to 30 seconds of background runtime" and "decides the best time to launch" [A] (https://developer.apple.com/documentation/backgroundtasks/bgapprefreshtask , https://developer.apple.com/documentation/backgroundtasks/choosing-background-strategies-for-your-app). `earliestBeginDate`: "the system doesn't guarantee launching the task at the specified date, but only that it won't begin sooner" [A].
- Also not run when the user turns off Background App Refresh or Low Power Mode is on, and rarely for apps the person seldom opens [T].
- Consequence: because weather is a pure function and presence-based, nothing needs to run in the background. The app computes on launch/foreground; the widget computes in its timeline provider; the notification planner schedules the next warning whenever the app is foregrounded (as `ReminderScheduler.refresh` already does). No `BGTaskScheduler` registration, no `fetch` background mode, no new review surface.

## 8. Accessibility and audio for weather visuals

- **Reduce Motion:** `accessibilityReduceMotion`: "UI should avoid large animations, especially those that simulate the third dimension" [A] (https://developer.apple.com/documentation/swiftui/environmentvalues/accessibilityreducemotion). HIG Accessibility: reduce "automatic and repetitive animations, including zooming, scaling, and peripheral motion"; replace axis transitions "with fades"; avoid "animating into and out of blurs" [A] (https://developer.apple.com/design/human-interface-guidelines/accessibility). Rain/snow/hail particle layers become a static illustrated overlay (tilted rain lines, frost rim on the pot) plus a text line. HIG Motion: "Make motion optional… avoid using it as the only way to communicate important information" [A].
- **Prefers Cross-Fade Transitions:** `UIAccessibility.prefersCrossFadeTransitions` (iOS 14) and the SwiftUI environment value `accessibilityPrefersCrossFadeTransitions` [T; both doc pages returned 404 on 2026-11-04, UNVERIFIED names]. Use cross-fades for weather arriving and clearing.
- **Flashing:** WCAG 2.3.1: nothing "flashes more than three times in any one second period", or flashes stay below the general and red flash thresholds (about a 341 x 256 px area at 1024 x 768) [P] (https://www.w3.org/WAI/WCAG22/Understanding/three-flashes-or-below-threshold.html). For a kids audience, aim for WCAG 2.3.2 (no flashes more than 3 per second regardless of size). Lightning: one soft, non-red, partial-screen glow, at least 1 s apart, no white full-screen flash; off when `MADimFlashingLightsEnabled()` is true ("whether the flashing lights setting is enabled on the device" [A], https://developer.apple.com/documentation/mediaaccessibility/madimflashinglightsenabled()), with Reduce Motion, Calm and Low Power, matching the thunder rules in STATUS (T-C).
- **VoiceOver:** post `AccessibilityNotification.Announcement` (iOS 17) once when the garden first shows the day's weather; priority default, not high ("Announcement priorities give you more control over which announcements people need to hear" [A], https://developer.apple.com/documentation/accessibility/accessibilitynotification/announcement). Each affected plant gets an `accessibilityValue` ("Frosty today, a warm cover helps") so state is never conveyed by art alone. Rescue puzzle: already tap-based and timer-free (`WakePuzzle` peek every 30 s).
- **Dynamic Type and color:** forecast and event lines use text styles and wrap at accessibility sizes (HIG: allow enlarging text "by at least 200 percent" [A]); pair every weather icon with a word (Differentiate Without Color [AC §7]).
- **Audio:** `.ambient`: "your app also works with the sound turned off… Screen locking and the Silent switch… silence your audio" [A] (https://developer.apple.com/documentation/avfaudio/avaudiosession/category-swift.struct/ambient). Route wind/rain beds through `Sound.swift`'s ambient session and its duck state, never through `ReadAloud`'s `.playback`. Gentle levels, slow attack, no sudden cracks (same constraints as the thunder asset). Haptics: low intensity, optional [AC §2].

## 9. Endgame-specific technical notes

- "All 50 plants" / "level 5 finished" should be **computed** from the collection every time (as pot unlocks are, STATUS T-D), never stored as a flag that could disagree across devices.
- Endgame loops that look like resets (new season, replant from seed, prestige) must be built on new monotonic counters plus derived state; the existing `max` merges otherwise restore old values (§0 row 2). Example: `seasonsCompleted` plus "plants grown this season" derived as `earnedCount - earnedAtSeasonStart`, where `earnedAtSeasonStart` is itself max-merged per season index, or simply a per-season insert-only row.
- New endgame content (more words, seasonal plant sets) can arrive via bank updates or Apple-hosted Background Assets [AC §7] with no schema change.
- Weather in the endgame works on a full garden because the overlay never touches collection counts; a "garden of 50" can host a weekly weather moment without any progress loss.
